# Аудит методов усреднения темпа/пульса (01.09.2026)

Вопрос владельца: корректны ли методы анализа — сохраняют ли реальный темп/пульс и
убирают ли мешающие скачки. Метод аудита: инвентаризация всех мест усреднения/окон +
эмпирические пробы на реальных raw-FIT (сплиты vs lap'ы часов как эталон, кросс-корреляция
окон, перекос очистки по всей истории из 36 файлов). Строки BACKLOG #277–#284.

## 1. Эмпирика: что подтверждено корректным

- **Per-km темп/пульс = lap'ы часов точь-в-точь** (#40: 6.99/7.22/7.02/7.14/6.88… vs
  6.98/7.22/7.02/7.14/6.88; HR по км идентичен). Верно и для `gap.per_km`, и для
  `km_segment_fallback` (карточка сегментов).
- **Интервальная сегментация** (#33): быстрый км пойман сегментом 4:54@172 (lap 4.87@172),
  второй быстрый 5:40@174 (lap 5.49@175) — лёгкое размытие границ, структура верна.
- **GAP-поправки по км легитимны**: «шумные» ±0.5 мин/км совпали с реальным рельефом
  (высоты 162→134 м); гистерезисный набор/спуск (`smoothed_gain_loss`) корректен.
- **Паузы**: на данных владельца стоячих точек ~0% (gross≈moving) — искажение от пауз
  сейчас не проявляется, но moving-времени в аналитике нет вовсе (см. §3.8).
- **smoothed_hr_peak** (скользящая медиана 5) работает по назначению.

## 3. Классы проблем (полная инвентаризация — 45 мест; приоритет ↓)

### 3.1 Потеря времени/дистанции при фильтрации (BACKLOG #277)
Пересборка дистанции (`analysis/__init__.py:76-95`) выбрасывает «слишком быстрые» дельты
из дистанции, но их **время остаётся** → avg_pace медленнее реальности (кейс №37 выше).
Родственное: `_compute_per_point_pace` (`segment_km.py:38`) выбрасывает точку вместе с её
dist/time-дельтами → длительность сегмента занижается, пауза «исчезает» из сегмента;
`_build_segments_from_boundaries` (`segment.py:178`) молча выкидывает сегменты <3 точек;
`km_segment_fallback` теряет дельту на каждой границе км → Σ сегментов ≠ итог.

### 3.2 Сводный GAP смещён вверх (BACKLOG #278)
`gap.py:143-147`: среднее темпов взвешено самим темпом = Σp²/Σp — контргармоническое,
систематически «медленнее» (км 4:00+6:00 → 5.2 вместо 5:00). Идёт в LLM
(`gap_avg_min_km`, `avg_pace_min_km`). Фикс: время/дистанция-взвешенное среднее.

### 3.3 Разрывы записи в зонах времени (BACKLOG #279)
`segment.py:78-81` и `session_metrics.py:56-61`: дельта времени зачисляется в зону HR
предыдущей точки БЕЗ ограничения на разрыв → пауза записи целиком уходит в зону последнего
пульса. HR-дропаут не разрывает Z4-отрезок → два интервала склеиваются → ложный
`interval_segment_too_long`. Готовая константа есть: `DRIFT_MAX_SAMPLE_GAP_SEC=10`
(применяется только в `effort.py:39-53`). Знаменатели двух реализаций расходятся:
`classify` делит на elapsed с HR-дырами (проценты занижены), `session_metrics` — на
HR-покрытое время.

### 3.4 Сырой max HR в UI (BACKLOG #280)
`__init__.py:104`: `max_heart_rate = max(hr)` без фильтра — одиночный спайк датчика
(cadence-lock) попадает в UI/Telegram. Фильтрованный `hr_peak_smoothed` уже считается,
но кормит только адаптивный max_hr. Диапазонного/скоростного санити для HR нет нигде.

### 3.5 Двойное усреднение зон (BACKLOG #281)
`repositories.py:88-98` (`zone_distribution` → скилл 80/20) и `history_tools.py:86-89`
(контекст LLM): вся длительность сегмента кладётся в зону его avg_hr → км на границе зон
уезжает целиком в одну; расходится с посекундным `computed.time_in_zones`. Отсюда же
«hard» recovery-кусок интервальной (§2).

### 3.6 cad==0 в средних (BACKLOG #282)
`__init__.py:219` (`avg_cadence`) и `segment_km.py:75`: каденс 0 (стояние) включён в
среднее; расходится с `cadence_block` (0 исключён, медиана) → UI-каденс систематически
ниже computed.

### 3.7 Хвостовой неполный км как полный (BACKLOG #283, связан с #259)
`gap.py:131-137`: км 200–1000 м выдаётся строкой per_km без пометки длины →
`quality_volume` считает его как 1.0 км; `hr_baseline.km_points` даёт полный вес в OLS
(шумная точка; вероятный вклад в заниженный наклон базовой линии — жалоба #259).
Последние 0–200 м отбрасываются вовсе.

### 3.8 Пакет прочего (BACKLOG #284)
- **Rolling pace**: заднее окно 250 м → лаг ~23 с, затухание пиков (§2); влияет на график
  и детекцию осцилляций, не на сегментные числа. Центрированное окно/меньший лаг — при case.
- **Клампы графика** (`utils.py:293`, 3.0<pace<10.0): точки ОТБРАСЫВАЮТСЯ, не обрезаются —
  спринты и паузы исчезают с графика, Chart.js рисует линию через дыру без индикации;
  HR первых ~250 м отсутствует (одна строка несёт HR+pace). Даунсемпл наивный (не LTTB).
- **interpolate_paces** (`utils.py:169`): хардкод 5.0 мин/км при полностью пустом ряде;
  «интерполяция» — плоское (prev+next)/2, не рампа.
- **Окна по точкам, не по времени** (`smooth_paces`, `_smooth`, `smoothed_hr_peak`,
  `smooth_altitudes`): при smart-recording ширина фильтра молча растёт ~в 5 раз.
- **elapsed vs moving**: drift/hr_stability на moving-времени (единственные), всё
  остальное на elapsed; moving-pace нигде не считается; гейт `pace_cv` для drift берётся
  с elapsed-стороны → ровный бег со светофорами получает reason="variable_pace".
- **`_ef`** (`effort.py:64-73`): скорость по всем сэмплам, HR — по HR-покрытым — смешение
  временных баз внутри drift_pct (ограничено гейтом покрытия 0.8).
- **GPS-мусор при HR≥130 не чистится** (`gps.py:45`): impossible-pace дельта с высоким
  пульсом остаётся в треке — мусор попадает в темповые метрики именно на качественных
  тренировках (компенсируется квалиметрией GPS от 01.09 только при большом масштабе).
- **oscillation.py**: end_idx последней фазы несогласован (off-by-one границы); слияние фаз
  не пересчитывает avg_pace/distance_m; `segment.py` не передаёт distances →
  дистанционный критерий фильтра фаз мёртв в ветке сегментации; hr_lag: нет ограничения
  dt, фолбэк подставляет нелагированный HR.
- **Атрибуция HR к дельте несогласована**: левый край в time_in_zones/km_segment_fallback,
  правый — в _compute_per_point_pace/build_moving_samples.
- **_adaptive_min_diff** (`segment.py:268 vs 271`): порог от СЫРОГО разброса темпа, поиск
  по сглаженному — один выживший выброс поднимает порог и прячет интервальную структуру.
- **Мёртвый код**: `compute_ewma`/`compute_moving_average` (`analytics_helpers.py`, никем
  не вызываются), `CALIBRATION_EWMA_ALPHA` (`coach/config.py:47`), метка
  `hr_pace_mismatch` (web), `seg_n` (`session_metrics.py`). Калмана нет; EWMA не подключён.
- **O(n²)**: `build_hr_pace_series` (3 полных скана на точку), `interpolate_paces`,
  merge-циклы — на часовой тренировке 1 Гц ≈ 13 млн операций ×3.

## 4. Общий вердикт

Числа, которые видит пользователь и коуч на уровне «км/сегмент» — честные (сверено с
часами). Скачки GPS режутся двумя фильтрами + квалиметрией (01.09); скачки пульса НЕ
фильтруются нигде, кроме hr_peak_smoothed. Главный системный грех — асимметрия «выбросили
дистанцию/точку, оставили время» и отсутствие moving-времени как понятия; главный
статистический — Σp²/Σp в сводном GAP. Большинство остального — краевые эффекты и
несогласованности между двумя реализациями одного и того же (зоны, атрибуция HR,
знаменатели), которые проявляются на дропаутах датчика и smart-recording, а не на
текущих чистых данных владельца.
