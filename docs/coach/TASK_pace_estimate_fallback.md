## 1. Симптом (инцидент 27.08.2026)

Утренний вердикт пришёл без ориентира по темпу и дистанции:

```
🚶 Восстановительный бег
Z1 и ниже · пульс до 125 уд/мин · 30 мин
Интенсив — не раньше 28.08 06:12
```

Владелец: **«От этого зависит маршрут, по которому я бегу. Мне важно знать, какое
расстояние нужно пробежать (примерно)»**. То есть строка-ориентир — не украшение,
а параметр, по которому планируется пробежка. Сейчас она пропадает именно там, где
нужна больше всего — на восстановительных.

## 2. Диагностика (проведена, факты проверены на проде)

Цепочка расчёта ориентира:

1. `predict_volume()` — `src/coach/prescriber.py` (HR-ветка): зона → `zone_ceiling_hr` →
   `expected_pace_at_hr(user_id, ceiling, db)` → `predicted = {pace_min_km, distance_km, …}`.
2. `expected_pace_at_hr()` — `src/services/insights_baseline.py`: ленивый бутстрап insights
   + `_collect_window_points()` (км-точки `(gap_pace, hr)` steady-типов
   `BASELINE_TYPES = easy/long/recovery` за `BASELINE_WINDOW_DAYS = 120` дней).
3. `pace_at_hr_band(points, hr_ceiling)` — `src/analysis/hr_baseline.py`: медиана темпа
   км-точек в **односторонней** полосе `[ceiling − BASELINE_PACE_HR_BAND_BPM(10), ceiling]`,
   минимум `BASELINE_PACE_BAND_MIN_POINTS(5)` точек, санити 3.5–12.0 мин/км, иначе `None`.

**Корневая причина.** Человек бегает в узком пульсовом коридоре, поэтому односторонняя
узкая полоса пуста для низких зон (recovery/Z1) и высоких (Z3+). Живые данные прода
(`user_id=2`, `max_hr=180`, 44 км-точки из 5 сессий за окно; основная масса пульса 128–146):

| Зона | Потолок | Точек в полосе | Результат |
|------|---------|----------------|-----------|
| Z1 | 125 | **2** | `None` — вот причина инцидента |
| Z2 | 144 | 24 | 6.79 мин/км — работает |
| Z3 | 156 | 3 | `None` |

## 3. Решения владельца (согласованы 27.08.2026)

- **Цифра нужна всегда**, когда есть хоть какая-то история; когда оценка грубая — честная
  пометка «прикидка, данных на этом пульсе мало» (не диапазон-вилка, не молчание).
- **Восстановительные остаются в режиме «по пульсу»** — вести их «по темпу» не нужно;
  темп и километраж там справочные ориентиры.

## 4. Что сделать — ступенчатая деградация A → B → C → D

### Уровень A (есть сейчас) — точная эмпирика
`pace_at_hr_band`: узкая односторонняя полоса, ≥5 точек. Логику не менять, только
добавить в результат `"quality": "band"`.

### Уровень B (новое) — широкая полоса + локальная поправка
Новая чистая функция `pace_at_hr_adjusted(points, hr_ceiling) -> dict | None`
в `src/analysis/hr_baseline.py`:

1. Подвыборка `S = {(p,h) : |h − ceiling| ≤ BASELINE_PACE_WIDE_BAND_BPM}` — полоса
   **двусторонняя**: для низких зон полезные точки лежат ВЫШЕ потолка. `len(S) < 5` → `None`.
2. `med_hr`, `med_pace` — медианы по `S`.
3. Гейт экстраполяции: `|ceiling − med_hr| > BASELINE_PACE_ADJUST_MAX_BPM` → `None`
   (уходим на уровень C).
4. Локальный наклон `b = OLS(h ~ p)` по `S`; если `sxx ≤ 0` или `b` вне
   `[BASELINE_HR_PACE_SLOPE_MIN, BASELINE_HR_PACE_SLOPE_MAX]` → `b = BASELINE_HR_PACE_SLOPE_DEFAULT`.
5. `pace = med_pace + (ceiling − med_hr) / b` (`b < 0`: потолок ниже медианы → темп медленнее).
6. Результат вне `BASELINE_PACE_PREDICT_MIN/MAX` → `None` (**не клэмп к границе**:
   приклеенное число сфабриковано, честнее упасть на уровень C).
7. → `{"pace_min_km", "n_points", "quality": "adjusted", "hr_delta_bpm", "slope_used"}`.

### Уровень C (новое) — типичный темп по типу тренировки
- `typical_pace_median(paces) -> dict | None` в `hr_baseline.py`: фильтр входа по санити,
  ≥`BASELINE_TYPICAL_MIN_SESSIONS` значений, медиана →
  `{"pace_min_km", "n_sessions", "quality": "typical"}`.
- `_typical_pace(user_id, workout_type, *, db)` в `insights_baseline.py`: медиана
  `training_sessions.avg_pace` за окно — сначала сессии того же
  `effective_training_type` (`src/coach/util.py`), при нехватке — все `BASELINE_TYPES`.
  Запрос лёгкий: только id/тип/avg_pace, **без `trackpoints_json`**.
- Зачем: у recovery-сессий `computed_json.gap.available = false` (км-точек нет вообще),
  но `avg_pace` есть — это единственный источник для них.

### Уровень D — данных нет
Строки нет, как сейчас.

### Композиция
`expected_pace_at_hr(user_id, hr_ceiling, *, db, workout_type=None, degraded_ok=False)`:
A → (если `degraded_ok`) B → C → `None`.

## 5. Критично для безопасности

`_pace_clamp_context()` (`src/coach/prescriber.py`) **должен остаться на уровне A** —
то есть вызывать `expected_pace_at_hr` без `degraded_ok`. Причина: его результат
(`PaceClampContext.safe_pace_min_km`) реально замедляет целевой темп в `safety.clamp()`
(`slowed = max(pace, safe_pace)`). Кормить в границу безопасности прикидку нельзя.
`degraded_ok=True` ставится ТОЛЬКО в `predict_volume` (справочный ориентир).
На это нужен отдельный тест-гвард.

**Не наступить на #259**: глобальная OLS-линия `HR = a + b·pace` имеет занижённый наклон
(b ≈ −2.4 против эмпирических ≈ −8), её инверсия уже давала нереальные темпы
(инцидент смоука 26.08.2026). Никакой глобальной инверсии — только локальный наклон
с санити-гейтом, который занижённый b закономерно не проходит → сработает дефолт −8.

## 6. Константы — `src/config/constants.py` (блок BASELINE_*)

```python
BASELINE_PACE_WIDE_BAND_BPM: Final[int] = 25      # двусторонняя полоса для уровня B
BASELINE_PACE_ADJUST_MAX_BPM: Final[int] = 15     # предохранитель экстраполяции (~1.9 мин/км)
BASELINE_HR_PACE_SLOPE_DEFAULT: Final[float] = -8.0   # bpm за мин/км (эмпирика владельца)
BASELINE_HR_PACE_SLOPE_MIN: Final[float] = -15.0      # санити локального OLS
BASELINE_HR_PACE_SLOPE_MAX: Final[float] = -4.0
BASELINE_TYPICAL_MIN_SESSIONS: Final[int] = 3     # минимум сессий для медианы avg_pace
```

Обоснование `ADJUST_MAX = 15`: живой кейс Z1 (Δ = 10 bpm) проходит, сомнительная
экстраполяция вверх для Z3 (Δ = 20) — нет, уходит на уровень C.

## 7. Проверка формулы на живых данных (уже прогнано 27.08.2026)

| Потолок | n | med_hr | med_pace | Δ | локальный OLS | b_used | Итог |
|---------|---|--------|----------|---|---------------|--------|------|
| 125 (Z1) | 43 | 135.0 | 7.02 | −10 | −1.88 (провалил гейт) | −8.0 | **8.27 мин/км → 3.6 км за 30 мин** |
| 144 (Z2) | 44 | 135.0 | 7.02 | +9 | −2.38 | −8.0 | 5.89 — но приоритет у уровня A (6.79) |
| 156 (Z3) | 37 | 136.0 | 6.95 | +20 | −0.57 | — | Δ > 15 → уровень C |

Для восстановительного 8:16/км → ≈3.6 км — реалистично. Поведение ровно такое,
как задумано, включая срабатывание дефолтного наклона.

## 8. Рендер — `src/coach/render.py`, `_hr_lead_lines`

Ветвление по `p.predicted.get("quality", "band")` — отсутствие ключа трактуется как
`band` (совместимость со старыми `predicted_json` в БД):

| quality | строка карточки |
|---------|-----------------|
| `band` | `Ориентир по твоим пробежкам: ~6:47/км → ≈4.4 км` (как сейчас) |
| `adjusted` | `Прикидка (данных на этом пульсе мало): ~8:16/км → ≈3.6 км` |
| `typical` | `По твоим прошлым таким пробежкам: ~7:10/км → ≈4.2 км (без привязки к пульсу)` |

Целевая карточка инцидента:

```
🚶 Восстановительный бег
Z1 и ниже · пульс до 125 уд/мин · 30 мин
Прикидка (данных на этом пульсе мало): ~8:16/км → ≈3.6 км
```

`render_prescription_short` — компактно, без пометки качества (нюанс живёт в полной
карточке). Инвариант §1.3 в силе: числа только из детерминированного рендера.
Опционально при реализации: для `adjusted`/`typical` округлять км до 0.5 — честная
точность; не блокер.

## 12. Риски

- **Утечка деградированной оценки в safety-clamp** — главный риск, закрыт дефолтом
  `degraded_ok=False` + тест-гвардом.
- **Ловушка #259** — закрыта санити-гейтом наклона, гейтом Δ ≤ 15 и санити результата.

- **`avg_pace` включает паузы/пешие вставки** — для recovery скорее плюс (реалистично для
  выбора маршрута); грубые выбросы отсекает фильтр санити перед медианой.

## 13. Вне этой задачи

Зеркальная ступенчатость для `hr_at_pace_band` (прогноз пульса в pace-режиме) —
**отдельная задача**. Там деградированная оценка питает `PaceClampContext.expected_hr`,
который триггерит замедление темпа в clamp, и требует собственного анализа безопасности.
Сейчас в pace-режиме при нехватке данных честно печатается «Пульс не прогнозирую —
мало данных на этом темпе», выбор маршрута это не ломает.

Родственное: **#263** (расширить выборку км-точек темповыми сегментами) — частично
снимет проблему для высоких зон, но не заменяет ступени B/C.
